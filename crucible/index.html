crucible · sandboxes for RL on code

tests it cannot fool.

Designed, built and measured by Sankur KunduOpen source (Apache-2.0) · page updated 15 Oct 2026

Training a model to write code with reinforcement learning means running its code thousands of times per step, safely. crucible builds a disposable sandbox for every answer from Linux primitives, with no virtual machines, and grades it with tests that never share a process with the model's code.

01 · Reward hacking

The grader a model cannot game

Unit-test rewards invite reward hacking, so the asserts run outside the sandbox and only plain values come back from it. tests/test_grader.py tries nine hacks against both graders:

HackcrucibleUsual grader
An always-equal objectfailpass
Exiting before the tests runfailpass
Forged test outputfailpass
sys.exit at importfailpass
Hacks that earn the reward0 of 94 of 9

During GRPO training every answer was also graded the usual way, to count the rewards a hack would have won.

02 · Isolation at speed

Faster than a bare Python

A warm process with the task's modules already imported forks each sandbox; a live sandbox can itself be forked mid-episode, its memory shared copy-on-write, so an agent can branch several attempts from one state. Four CPUs:

bare Python, no isolation19.8 ms
crucible, fully isolated5.3 ms

Time to start a sandbox. 8 branches of a 256 MB sandbox use 508 MB instead of 2,304 MB copied (bench/spawn.py, bench/fork.py).

03 · Training with it

RL on code, graded safely

Served through OpenEnv's interface, crucible graded every answer in GRPO training on ratchet. MBPP, 499 test tasks, two Tesla T4s:

Greedy pass@1Seed 0Seed 1Seed 2Mean
Before training34.9%34.9%
After 100 GRPO steps38.9%38.1%38.9%38.6%
Tasks fixed / broken44 / 2448 / 3248 / 28

Paired test over the 499 tasks: p = 0.013. 115 of the 140 fixes were answers that already ran and gave wrong results: the gain is mostly correctness, not formatting (scripts/pool_m3.py).

What crucible adds

Safe rewards for code-writing models

The infrastructure that RL on code depends on, built from Linux primitives and measured against the attacks a model actually finds.

  1. Sandboxes from Linux primitives

    Namespaces, limits, no capabilities and seccomp: 5.3 ms per isolated sandbox, no VMs.

  2. A grader that resists hacking

    Tests outside the sandbox: 0 of 9 hacks pass, against 4 of 9.

  3. Branching episodes

    Fork a live sandbox in 4.5 ms, copy-on-write: a rollout tree grown from forks needs up to 10.9× less environment time than replaying each path, and every leaf keeps the state the episode had.

  4. A measured training gain

    34.9% → 38.6% MBPP pass@1, three seeds, p = 0.013.

Where it falls short

A 0.5B model and 100 steps, so the gain is a few points, and each run also broke 24 to 32 tasks it had solved before.
