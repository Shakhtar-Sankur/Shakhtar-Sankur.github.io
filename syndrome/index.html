syndrome · quantum error correction

bit-identical to IBM.

Designed, built and measured by Sankur KunduOpen source (Apache-2.0) · page updated 22 Oct 2026

IBM plans to build fault-tolerant quantum computers on bivariate bicycle codes such as the [[144,12,12]] gross code, decoded by Relay-BP, IBM's own algorithm. syndrome is an open GPU implementation of it, checked against IBM's reference code shot by shot: every decoding, every posterior in float64 and float32, every iteration count. On a T4 it decodes 4.0× faster than IBM's decoder on the whole CPU of the same machine.

01 · Why

A decoder has to keep up

A quantum computer corrects its errors only if a classical decoder works out what went wrong, round after round, as fast as the hardware produces syndromes: about once a microsecond on superconducting devices.

IBM's codes

Bivariate bicycle codes protect 12 logical qubits with 144 data qubits at distance 12, far fewer qubits than a surface code needs for the same protection.

IBM's decoder

Relay-BP (Müller et al., arXiv:2506.01779) runs belief propagation in legs, each with different memory strengths, relaying posteriors from leg to leg until enough solutions are found.

The gap

IBM's open reference runs on a CPU: 1.65 s per shot at p = 0.3% and 5.1 to 5.5 s at p = 0.4% on one core here. NVIDIA's GPU Relay-BP is closed source. No open GPU implementation had been checked against IBM's.

04 · Speed

4.0× IBM's decoder on the whole CPU

1,024 shots at p = 0.3% on the T4, and the same 1,024 shots through IBM's decoder in its parallel batch mode on all 4 CPU threads of the same Kaggle machine. Both predicted the same logical observables on every shot.

MessagesIBM, all 4 threadssyndrome, thread per checksyndrome, warp per checkvs IBM
float641,051 ms per shot453 ms per shot298 ms per shot3.5×
float32790 ms per shot330 ms per shot199 ms per shot4.0×

How: float32 messages, matching IBM's own float32 decoder bit for bit (a T4 runs float32 32× faster than float64); one warp of 32 threads per check, reading a check's ~226 edges side by side and combining the two smallest magnitudes with shuffles, which changes no bits; and a shared queue, so a shot needing all 301 legs no longer holds back the rest. Together 2.0× faster per shot than the first GPU build. Against one CPU thread the float32 kernel is 6.2× faster. Raw output: results/m2/m2_t4_f64_f32_kaggle_log.jsonl.

What syndrome adds

How the match was made

Bit-for-bit agreement does not happen by accident in floating point; each of these was needed.

  1. One source, two targets

    The check and variable updates are written once in a header that compiles for the CPU and a CUDA thread block, following IBM's code operation for operation.

  2. Same rounding, both precisions

    Min-sum with the two smallest magnitudes, Mem-BP priors, sums in IBM's order, the float32 priors rounded exactly as IBM's, and fused multiply-add turned off, because it rounds once where IBM's code rounds twice.

  3. Independent shots

    IBM's decoder draws memory strengths from one generator shared across shots; syndrome uses IBM's explicit-table option so thousands of shots can be decoded at once and each compared exactly.

  4. Reproduced before compared

    IBM's own decoder reproduced IBM's published error rate here before any GPU number was reported.

Where it falls short

The speed is measured against a small 4-thread cloud CPU, on which IBM's batch mode gained only 1.6× over one thread; a large server would narrow the gap, and a per-watt comparison on matched hardware is still to do. It is a throughput result: with 120 shots in flight each shot spends about 24 s on the GPU, so latency per round is not yet addressed. The exact match is shown on 256 shots at two noise levels in one basis; GPU error rates over millions of shots, the X basis and streaming (sliding-window) decoding are still to do.
