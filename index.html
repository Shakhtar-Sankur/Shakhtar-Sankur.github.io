quorumdb.

          

        

        

          

            
A distributed SQL database that psql connects to, built one proven layer at a time.

            
A crash-safe LSM storage engine, Raft consensus, a sharded multi-Raft store that splits and
               rebalances itself, and ACID transactions across machines at snapshot and serializable
               isolation. Every layer is tested the way FoundationDB is: one seed replays a whole run of
               random work, crashes, partitions and clock skew, exactly, and a checker proves every
               history linearizable or serializable. It speaks the PostgreSQL wire protocol, with joins,
               aggregates, EXPLAIN and serializable transactions. The transaction protocol is model-checked
               in TLA+, a TPC-C-derived benchmark drives the whole stack, and a time-travel debugger steps
               any simulated Raft cluster event by event, and backward by replay.

            
    
              
  • 10,000Simulated Raft clusters through 610K crashes, zero safety violations

  • 1,503tpmC on a TPC-C-derived benchmark, serializable, consistency checks passing
    • 
              
  • 337KStates TLC checked in the TLA+ model of the transaction protocol, zero violations
    •

ML compilerRust · zero dependenciesSIMD & CUDA code generationTensor coresAuto-tuning

            
kiln.

          

        

        

          

            
An ML compiler that turns a PyTorch model into fused, auto-tuned code for CPUs and NVIDIA GPUs, and beats torch.compile on CPU.

            
The pipeline of XLA, TVM and torch.compile, end to end and from scratch: it decodes ONNX, folds
               constants and canonicalizes the graph, fuses it into a few kernels over an affine loop IR, generates
               SIMD C, compiles and loads it at run time, and auto-tunes every matrix multiply on the machine it
               runs on. A memory planner packs every intermediate into one arena. Its GPU backend generates CUDA
               (fp16 tensor-core matmuls, split-K, CUDA graphs), compiles it with NVRTC at run time and tunes it on
               the device. On BERT and SmolLM2 its output matches PyTorch's. On 4 CPU cores it is fastest of five
               engines. On an NVIDIA T4 in fp16 it beats torch.compile on SmolLM2 and an MLP, and trails it on BERT.
               In fp32 the cuBLAS-based engines stay ahead. CI checks the generated C and CUDA against PyTorch with
               each optimisation off and under every tuned schedule, on an emulator of the CUDA execution model.

            
    
              
  • 117 msBERT on 4 CPU cores, 8 × 128 tokens: torch.compile 149, ONNX Runtime 153, JAX/XLA 189, PyTorch 198
    • 
              
  • 7.9 msSmolLM2-135M on an NVIDIA T4, fp16 tensor cores: 1.65× faster than torch.compile (13.1 ms)
    • 
              
  • 3.7×Faster than torch.compile on the MLP on the T4 (0.30 vs 1.10 ms); auto-tuning is worth up to 1.70×
    • 
              
  • 16 MBArena holding BERT's 381 MB of intermediates, planned at compile time

GPU & TPU kernel compilerRust · zero dependenciesCUDA · Metal · PallasTensor coresLLM engine

            
tessel.

          

        

        

          

            
A Triton-style tile language and its compiler: a kernel written once, compiled for NVIDIA GPUs, Apple GPUs and Google TPUs, fast enough to run an LLM at vLLM's speed.

            
Kernels are written against tiles, small blocks of values, and the compiler decides which thread holds
               which element: it gives every tile a linear layout, as Triton does, and generates CUDA for tensor cores
               with ldmatrix, mma.sync, XOR-swizzled shared memory and software-pipelined loads, tuned on the GPU it
               runs on. The same kernels compile to the Metal Shading Language for Apple GPUs and to Pallas for TPUs,
               where range analysis must prove every block access in bounds or the kernel is refused. On top of it
               sits an LLM engine whose every GPU operation is a tessel kernel: fused QKV projection, rotary
               embeddings, a paged KV cache, grouped-query attention, SwiGLU, continuous batching, packed prefill and
               CUDA graphs. On TinyLlama-1.1B its generations are identical to vLLM's, token for token. CI checks
               every kernel against a reference interpreter on an emulator of the CUDA execution model, compiles it
               with NVRTC, runs it in Pallas's TPU interpret mode and compiles it with Apple's Metal compiler. It has
               not yet been timed on a TPU or an Apple GPU.

            
    
              
  • 1.05×vLLM 0.30's throughput serving TinyLlama-1.1B, 32 requests at once on a T4, in two sessions (1858 vs 1764, 1884 vs 1798 tokens/s); with 8, 0.94–0.99×
    • 
              
  • 1.00×cuBLAS on fp16 GEMM at 1024³ and 2048³, 1.04× at 4096³; 0.71× before shared memory was swizzled
    • 
              
  • 1.3–1.9×Faster than PyTorch's scaled_dot_product_attention on causal attention, sequence 512 to 4096
    • 
              
  • 3Targets from one kernel: CUDA (tested on a T4), Metal and Pallas (compiled and checked in CI)
    •

Distributed trainingPython · C++ · CUDADDP · ZeRO/FSDP · pipelinesOwn all-reduce, no NCCL

            
tandem.

          

        

        

          

            
Distributed training from scratch, on its own collectives: no torch.distributed, no NCCL, and the same losses and weights as PyTorch, to the last bit.

            
tandem implements the parallelisms behind large-model training on PyTorch tensors and autograd:
               DDP with gradient buckets reduced as backward fills them, ZeRO-1, 2 and 3 (sharded optimizer state,
               gradients and, FSDP-style, parameters gathered just before use and prefetched), and GPipe and 1F1B
               pipeline schedules in Megatron-LM's order, all over its own ring all-reduce, reduce-scatter and
               all-gather. On two T4 GPUs, DDP and every ZeRO stage end 20 training steps with exactly the losses
               and weights of PyTorch's DDP and FSDP. Its collectives then moved into a C++ engine, a PyTorch C++
               extension: lock-free single-producer, single-consumer rings in shared memory and a progress thread
               on the CPU, and on GPUs buffers shared through CUDA IPC, ordered by interprocess events and reduced
               by a fused CUDA kernel, so the host never waits for a piece. Where it still falls short: its DDP
               reaches 86% of PyTorch DDP's throughput, and the C++ engine has not yet been timed against NCCL
               across two GPUs.

            
    
              
  • 0.0Largest weight difference from PyTorch DDP and FSDP after 20 steps on two T4s, for DDP and ZeRO-1, 2 and 3
    • 
              
  • 1.6–2.8×Faster all-reduce with the C++/CUDA engine than the Python one on a T4, 64 KB to 64 MB
    • 
              
  • within 2%Of NCCL's all-reduce bandwidth at 64 to 256 MB, with the Python engine across two T4s
    • 
              
  • 17% / 32–52%Less memory per GPU with ZeRO-3 than DDP, and with 1F1B than GPipe, on an 86M-parameter GPT
    •

LLM inferenceC++20 · CUDA · SwiftPrefill/decode disaggregationFlash-attention kernelsKV-cache streamingFault-tolerant

            
relay.

          

        

        

          

            
LLM serving split in two: prompts on prefill workers, tokens on decode workers, and the KV cache streamed between them while the prompt is still being processed.

            
relay's C++20 and CUDA engine has a paged KV cache, continuous batching with chunked prefill,
               preemption and prefix caching, and attention kernels I wrote for it: flash attention on tensor cores
               (WMMA, online softmax) for prompts, and flash-decoding over the paged cache for generation, which
               splits long contexts into slices and reads each K/V row once for all the query heads that share it. Its transfer engine sends each layer's cache as soon as that layer
               finishes, over TCP or a shared-memory ring; on a GPU a gather kernel packs the layer into pinned
               memory on its own copy stream, so the copy overlaps the next layer's compute. A decode worker with no
               room says so and recomputes instead of stalling the stream. In front of the worker processes sits a
               control plane in Swift, calling the engine through Swift's C++ interoperability: a tokenizer and chat
               templates, an OpenAI-compatible streaming API, a router that sends prompts with the same beginning to
               the worker whose cache already holds it, and admission control. It is fault-tolerant: a worker that
               dies, freezes or stalls is caught by connection, heartbeat and progress watchdogs, and each of its
               requests resumes on another worker from where it stopped, with exactly the tokens it would have had.
               The chaos tests that prove it found three real bugs on the way. Where it still falls short: int8
               weights help only a single sequence (from batch 8 up, fp16 on tensor cores is faster), and it has not
               yet been benchmarked against colocated serving or vLLM on several GPUs.

            
    
              
  • 8.7×Faster 2,048-token prefill on a T4 with the new attention kernels (TinyLlama, 3.7 s to 0.43 s; 10.4× on SmolLM2), and 5.4× faster decode steps for 32 sequences at 2,048 tokens, logits within 0.1%
    • 
              
  • 99–100%Of the KV transfer hidden by streaming on a T4: 46 MB after a 2,048-token prompt, 21.6 ms exposed when sent after prefill, 0.08 ms when streamed
    • 
              
  • bit-identicalOutput whether a request is batched, served from the prefix cache, preempted, or split across prefill and decode workers
    • 
              
  • 3 modelsSmolLM2, Qwen2.5 and TinyLlama: logits match Hugging Face, and the Swift tokenizer and chat templates match it exactly
    • 
              
  • 384 / 384Requests identical to a fault-free run while workers were SIGKILLed 60 times at random (SmolLM2, 3 seeds, two cluster shapes), none failed
    • 
              
  • 47%Fewer tokens computed with the prefix cache on a shared-prompt test (339 to 179), with the same output
    •

RL post-trainingPython · PyTorch · C++/CUDAGRPOIn-place weight syncMixed precision2× T4

            
ratchet.

          

        

        

          

            
The training loop behind reasoning models, built end to end: an engine generates answers, a reward scores them, a trainer learns from them, and the new weights go straight back into the engine.

            
ratchet runs GRPO, the algorithm used to train DeepSeek-R1, on two GPUs. relay, my C++/CUDA engine,
               generates eight answers per maths problem through a C API I added, with the log-probability of every
               token; a PyTorch trainer, built in relay's exact weight layout so that a sync is a copy, scores them
               against the reference answer, normalises rewards within each group and takes a PPO-clipped step with
               AdamW. The new weights then go into relay in place on the GPU: fp32 to fp16 on the device, a peer copy
               when trainer and engine sit on different GPUs. Two GPUs can be used two ways: colocated, where both
               generate and then both train, with gradients averaged by tandem, my own data-parallel library; or split,
               where one GPU generates the next batch while the other trains on this one, with partial rollouts so a
               few long answers do not hold up a step. The hardest part was a bug no CPU test could show: relay
               stores its weights in fp16, and an update of about 10-6 is smaller than half an fp16 step for most
               weights, so relay rounded the updates away and sampled from a policy the trainer never had. The
               trainer now computes with the same fp16-rounded weights and keeps fp32 master weights. Where it still
               falls short: one training run per mode on a 0.5B model, so the gain is a few points, not a benchmark result.

            
    
              
  • 48.1% → 52.5%Qwen2.5-0.5B on all 1,319 GSM8K test problems after 100 GRPO steps on two T4s (colocated); 47.8% → 50.2% split
    • 
              
  • 369×Faster weight sync in place on the GPU than a full reload: 0.017 s instead of 6.3 s for 494M parameters, identical rollouts
    • 
              
  • 5.2 → 0.04Largest gap between the engine's and the trainer's log-probabilities after an update, before and after the fp16 fix
    • 
              
  • 1.9×Faster steps when one GPU generates the next batch while the other trains: 49.1 s to 25.6 s
    • 
              
  • 27×Faster rollouts, 34 to 931 tokens/s, after sampling stopped sorting the 151,936-token vocabulary for every token
    •

Mixture-of-experts servingCUDA · C++ · PythonExpert parallelismPeer-to-peer dispatchTensor cores2× T4

            
switchyard.

          

        

        

          

            
A mixture-of-experts model served across two GPUs, with everything below the model written from scratch: the kernels, the dispatch between GPUs, and the measurements of what load balancing is worth.

            
OLMoE-1B-7B sends every token to 8 of the 64 experts in each layer. switchyard gives each GPU half of
               every layer's experts and its own share of the requests. My CUDA kernels route each token in one warp,
               sort the rows by expert with a block-wide prefix scan and no atomics, and run every expert in a single
               launch: a tensor-core grouped GEMM with SwiGLU fused into its epilogue, and for decode a grouped GEMV
               that streams expert weights at 73% of the T4's memory bandwidth. Instead of NCCL, a kernel writes the
               rows bound for the other GPU straight into its memory over peer-to-peer, ordered by CUDA events, and the
               results come back to exactly where the sender's sort expects them, so the output matches one GPU bit for
               bit. Each GPU is driven by its own thread; getting that right meant finding two cross-stream races that
               only appeared without CUDA_LAUNCH_BLOCKING. Where it falls short: over PCIe, splitting the experts is never
               faster than keeping all 64 on one GPU; here it buys memory, 7.6 GiB per GPU for a 13.8 GB model.

            
    
              
  • 2.2×Faster decoding than Hugging Face transformers on the same two T4s: 112 vs 52 tokens/s at batch 8; 823 tokens/s at batch 64
    • 
              
  • Bit-identicalExpert-parallel output equals the single-GPU layer exactly; greedy output identical to transformers on 7 of 8 prompts over 32 tokens
    • 
              
  • 5.4–7×Faster decode MoE layer than a per-expert PyTorch loop (1–8 tokens), 1.9–2.3× faster than a cuBLAS loop over sorted rows
    • 
              
  • 1.25×Faster than NCCL's all-to-all at 256 tokens per GPU with my peer-to-peer dispatch; level at 16–64, slower at 1 and 1,024
    • 
              
  • 12.9 → 20.2WikiText-2 perplexity when experts drop the tokens they have no room for, even at capacity factor 2; so switchyard never drops one
    •

      The thesis
      
The people who move the world's goods have no platform of their own.

      

        

          01 — The problem
          
One person, many apps

          
A Swiggy rider, an Uber driver and an Amazon Flex courier are often the same person —
             but no platform connects those identities. More than half of gig workers operate
             across several platforms at once, and each one sees only its own slice.

        

        

          02 — Why it compounds
          
No history, no credit

          
Without a single verifiable work history, banks read gig workers as unemployed and
             refuse them credit. The fragmentation is not an inconvenience; it is the thing
             keeping people out of the financial system.

        

        

          03 — What I do about it
          
Build it, then prove it

          
I co-founded Gigzen in 2026 and build its software: the rider platform, the backend
             it runs on, the testing tool that proves it works, and the record of every test that
             was run — including the ones that failed.

          Mixture-of-experts · CUDA · Multi-GPU
switchyard

          
Mixture-of-experts serving with expert parallelism, from scratch: OLMoE-1B-7B across two GPUs on my own
             CUDA kernels (routing, sorting, tensor-core grouped GEMM and GEMV) and a peer-to-peer dispatch in place of
             NCCL. Bit-identical to one GPU and 2.2× faster decoding than Hugging Face; measured on real text,
             dropping overflow tokens raised perplexity from 12.9 to 20.2, so it never drops one.

          View source 
        
        
          RL post-training · PyTorch · C++/CUDA
ratchet

          
Reinforcement-learning post-training (GRPO) from scratch on two GPUs: rollouts with per-token
             log-probabilities on my own C++/CUDA engine, a PyTorch trainer data-parallel on tandem, and weights synced
             back in place on the GPU, 369× faster than a reload. 100 steps raised Qwen2.5-0.5B on GSM8K from
             48.1% to 52.5%, after I found and fixed fp16 rounding that silently discarded the training updates.

          View source 
        
        
          LLM inference · C++/CUDA · Swift
relay

          
A disaggregated, fault-tolerant LLM inference cluster: prefill and decode workers in C++20/CUDA with my own flash-attention
             and flash-decoding kernels (2,048-token prefill 8.7× faster on a T4), a paged KV cache and prefix caching; a KV-cache transfer engine that streams each layer while the
             next computes, hiding 99–100% of the transfer on a T4; and a Swift control plane (Swift–C++
             interop, OpenAI-compatible streaming API, prefix-aware routing). Output matches Hugging Face, and
             survives worker crashes: 384 of 384 requests identical through 60 random kills.

          View source 
        
        
          ML systems · Distributed training · C++/CUDA
tandem

          
Distributed training from scratch on its own collectives, with no torch.distributed or NCCL: DDP,
             ZeRO-1/2/3 (FSDP-style sharding) and GPipe/1F1B pipelines. On two T4s it trains bit-identically to
             PyTorch DDP and FSDP; its all-reduce is within 2% of NCCL's bandwidth at 64–256 MB; its C++/CUDA
             engine (lock-free shared-memory rings, CUDA IPC, a fused reduce kernel) is 1.6–2.8× faster
             than its Python engine on a T4.

          View source 
        
        
          Open source · PyTorch Inductor · under review
PyTorch PR #199875

          
A fix to the torch.compile compiler, under review: in deterministic mode, eager PyTorch fills
             torch.empty with NaN, and compiled code did not. It now does, while Inductor's own internal buffers
             stay unfilled, which is why an earlier fix was reverted. Tested on CPU and on a T4 GPU.

          ML systems · GPU kernels · Compiler
tessel

          
A Triton-style tile language and compiler in Rust with zero dependencies: linear layouts, CUDA for
             tensor cores (ldmatrix, mma.sync, swizzled shared memory, pipelining, auto-tuning), plus Metal and
             Pallas (TPU) backends. On an NVIDIA T4, GEMM at parity with cuBLAS and attention 1.3–1.9×
             faster than PyTorch; an LLM engine on its kernels matches vLLM's output token for token at 1.05×
             its throughput with 32 requests.

          View source 
        
        
          ML systems · Compiler · Code generation
kiln

          
An ML compiler in Rust with zero dependencies: ONNX import, constant folding, operator fusion over an
             affine loop IR, SIMD C and CUDA code generation (tensor cores), auto-tuners and a memory planner. Output
             matches PyTorch. On 4 CPU cores it runs BERT in 117 ms, faster than torch.compile (149), ONNX Runtime
             and JAX/XLA. On an NVIDIA T4 in fp16 it runs SmolLM2 1.65× faster than torch.compile.

          View source 
        
        
          ML systems · LLM inference · RAG
ferrolm

          
An OpenAI-compatible LLM server and retrieval stack in Rust with zero dependencies: paged KV cache,
             continuous batching, prefix caching and speculative decoding on hand-written AVX-512 kernels, plus
             int8/int4 quantization (AWQ), BERT embeddings and HNSW / IVF-PQ vector search at FAISS-level recall.
             3.4× the throughput of one-at-a-time serving; retrieval lifts SQuAD answer F1 from 15 to 48.

          View source 
        
        
          Systems · Distributed database

A distributed SQL database in Rust with zero dependencies that psql connects to: LSM

          Systems · Fault injection
faultline

          
Jepsen-style testing of real etcd clusters in Rust: network partitions, kill -9 crashes and process
             pauses across four etcd release lines and 1.26M operations. Linearizability and watch guarantees held;
             it traced lost updates under etcd's locks to a paused leader applying a timed-out write 6 s late.
